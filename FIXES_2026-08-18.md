# Fixes — Edit Profile image upload & Library screen scrolling

Date: 2026-08-18
Scope: `src/screens/EditProfileScreen.js`, `src/screens/LibraryScreen.js`, `app.json`
Rule followed: no UI, layout look, or typography changes — spacing/logic only.

---

## 1. Settings → Edit Profile → profile image update failing

**File:** `src/screens/EditProfileScreen.js`

### What was wrong
- On Android, `expo-image-picker` frequently returns a `content://` URI
  instead of a `file://` path. Handing that URI straight into a `FormData`
  body for the Cloudinary upload is unreliable across Android
  versions/OEM gallery apps and is the most common cause of an upload
  "error" that only reproduces on device (not in every environment).
- The upload call had no timeout, so a bad connection could leave "Saving…"
  spinning with no error ever surfaced.
- Cloudinary error responses (e.g. an upload preset that isn't enabled for
  unsigned uploads) were not read from `response.status` and could be
  swallowed as a generic "Upload failed".
- `expo-image-picker` had no Expo config plugin entry in `app.json`, which
  can cause inconsistent permission-prompt behavior in EAS/production
  builds vs. Expo Go.

### What changed
1. Added `cacheLocalCopy()` — copies the picked asset into
   `FileSystem.cacheDirectory` (via `expo-file-system`, already a project
   dependency, no new install) before it's previewed or uploaded. Guarantees
   a real `file://` URI on both platforms.
2. `uploadImageToCloudinary()` now:
   - Has a 30s timeout via `AbortController` (fails fast with a clear
     message instead of hanging).
   - Checks `response.ok` and surfaces Cloudinary's own `error.message`
     when the upload preset/config itself is the problem.
   - Normalizes MIME type (`jpg` → `image/jpeg`, etc.).
3. `handleSave()` now catches upload failures separately from save
   failures, keeps the picked image on screen so the user doesn't lose it
   and can just retry, and — on success — clears `tempImage`/syncs
   `form.photoURL` so navigating back in and out doesn't imply a stale
   upload of the same image.
4. Added `expo-image-picker` to the `plugins` array in `app.json` with an
   explicit photo-library usage string (existing `NSPhotoLibraryUsageDescription`
   on iOS was already present and is unaffected).
5. No visual changes: same avatar circle, same camera button, same loading
   spinner, same toast system, same copy — only the logic under the hood.

### ⚠️ One thing to verify on your end (not fixable from code)
If uploads still fail after this fix, check the Cloudinary dashboard for
cloud name `dhliwva4d` → **Settings → Upload → Upload presets** → the
preset `faithframes_uploads` must exist and be set to **Unsigned**. The
error toast will now show Cloudinary's own message (e.g. "Upload preset
not found") if this is the cause, since that's no longer swallowed.

### Persistence after restart
Already worked correctly and is unchanged: `updateUserProfile()` writes
`photoURL` to the user's Firestore doc, and `AuthContext`'s
`onAuthStateChanged` listener re-fetches that doc on every app launch, so
the new photo is what's shown after a restart.

## 2. Library screen — 5 cards must fit with no scrolling

**File:** `src/screens/LibraryScreen.js`

### What was wrong
The screen already had a partial fix (a `scale` factor that shrinks
spacing on short screens) from an earlier pass, but the content was still
wrapped in a `ScrollView`, so it could still scroll, and the scale factor
was computed as a flat `windowHeight / 852` ratio that didn't actually
account for the safe-area insets or the real bottom tab bar height —
so the "fit" was approximate, not guaranteed.

### What changed
1. **Removed `ScrollView` entirely** — replaced with a plain `View`
   (`flex: 1`), so there is no scroll gesture at all.
2. **Rewrote the scale calculation** (`useLibraryScale`) to compute the
   actual available height:
   `windowHeight − insets.top − tabBarHeight − safetyGap`, where
   `tabBarHeight` mirrors the real bottom tab bar
   (`src/navigation/MainNavigator.js`, `styles.navBar.height = 72` +
   `Math.max(insets.bottom, 10)`), instead of guessing from a flat
   reference height.
3. Compared that available height against the content's known natural
   height (summed from the actual style constants used lower in the file,
   with a small buffer) to derive the scale factor, so cards always fit
   above the tab bar on any device size — phones with tall/short aspect
   ratios, tablets, devices with/without a notch, etc.
4. Content bottom padding now exactly reserves the tab bar's real height
   instead of a generic spacer view.
5. **No visual changes**: same 4 feature cards + Live Worship Room card,
   same order, same colors/icons/fonts, same animations. Only the spacing
   that was already scale-driven now scales off an accurate number, and
   there's no more scroll container.

## How to test

### Edit Profile image
1. Open the app → **Settings → Edit Profile**.
2. Tap the camera icon on the avatar → pick a photo from the library.
   - On Android specifically, confirm the picked image preview shows up
     immediately (this exercises the new local-copy path).
3. Tap **Save Changes**.
   - Expect either a success toast + navigate back, or — if something is
     genuinely wrong (e.g. no network, or the Cloudinary preset issue
     above) — a specific error toast, and the app must **not** hang on
     "Saving…" indefinitely (verify by testing with airplane mode: it
     should show a timeout/network error after ~30s, not spin forever).
4. Re-open the app (force close + relaunch, or Fast Refresh a clean login)
   → **Settings → Edit Profile** → confirm the new photo is still shown
   (pulled fresh from Firestore).
5. Repeat on both iOS and Android — pay particular attention to Android,
   since that's the platform the `content://` URI issue affects.

### Library screen
1. Open the **Library** tab.
2. Confirm all 5 cards (Daily Verse, Prayer Room, Wallpaper, Scripture
   Videos, Live Worship Room) are fully visible with no scrolling, and the
   Live Worship Room card sits fully above the bottom tab bar.
3. Try this on a few different screen sizes/devices if available (e.g. a
   small phone like iPhone SE / a compact Android device, and a larger
   phone) — content should shrink slightly on the smallest screens but
   never require scrolling or get cut off by the tab bar.
4. Rotate-locked portrait is assumed (app is portrait-only per `app.json`).

### General
- Watch the Metro/device logs while testing both flows — the new code
  logs warnings prefixed `[EditProfile]` for any failure path, which will
  help pinpoint the exact cause if an issue persists.
- No other screens or shared components were touched — `git diff` should
  show changes scoped to `src/screens/EditProfileScreen.js`,
  `src/screens/LibraryScreen.js`, and `app.json` only.
